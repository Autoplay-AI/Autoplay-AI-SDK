Most AI chat widgets wait for users to ask a question. Proactive support flips that: your app watches what users do in real time, detects friction patterns, and surfaces help automatically — in the right place, at the right moment, with the right context already loaded.

## What you'll build

A proactive guidance layer on top of `InkeepEmbeddedChat` that:

- **Detects repetitive actions** — e.g. a user opening the same panel three times without completing it.
- **Surfaces a contextual offer** — a popup appears with a summary of what the user is struggling with.
- **Offers two resolution paths:**
  - **Show me** — a step-by-step in-app tour that highlights exactly what needs attention.
  - **Open chat** — `InkeepEmbeddedChat` opens with an `introMessage` already loaded from the user's session context, so the AI's first message references the exact issue.

The AI never starts cold. It knows what the user was doing before they even typed a word.

## How it works

```
User actions (clicks, page views, errors)
        │
        ▼
   FastAPI bridge  ──  httpx pull from the Autoplay connector
        │              (stateless REST read, keyed by user_id)
        │
        │  ≥ 3 repetitive actions without completion?
        ▼
   SSE event → proactive popup appears in your app
        │
   ┌────┴────────────────────┐
   ▼                         ▼
Show me                  Open chat
(in-app guided tour)     (InkeepEmbeddedChat +
                          user context as introMessage)
```

The bridge owns all trigger and context logic. Inkeep stays a clean conversational layer — it receives context, not raw events. The ingestion half of this diagram is a stateless pull: the bridge asks the connector for a user's recent activity exactly when it needs it, rather than holding a stream connection open. The "SSE event → proactive popup" half is your own app's internal channel for pushing the toast to the frontend — unrelated to how Autoplay delivers activity, and unchanged here.
